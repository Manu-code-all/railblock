## 2 · THE PROBLEM STATEMENT

**PS ID SIH2026027 — Automatic Block Planning for Indian Railways**
Ministry of Railways · Category **Software** · Theme **Smart Automation**

Three maintenance departments — Engineering (P.Way), Signalling & Telecom, and
Traction (OHE) — each request track possession ("blocks") independently. Nobody
sees the others' plans, so blocks clash, get cancelled on the day, maintenance
slips and trains are delayed.

**Solution name: RailBlock.** One planner takes all three departments' demands
plus the timetable and returns a single conflict-free schedule that CP-SAT
*proves* optimal — or, when the demands genuinely cannot all fit, the exact
minimal set of requests in conflict.

### Why this one won the internal ranking

- **Precedent:** SIH 2025 was won by KMRL train-induction scheduling — the same
  class of railway optimisation problem.
- **Provable:** the solver certifies optimality. No accuracy figure to defend.
- **Passes both filters cleanly** — pure operations research, zero training.
- **Under-picked** — student teams gravitate to chatbots and detection models.
- Runner-up was **PS 117** (sovereign agentic AI, MRPL): higher ceiling, far
  higher variance, needs a GPU at the venue. Rejected as a gamble.

### ⚠ One thing never resolved

The portal list the user screenshotted showed **"AI-Driven Train Induction
Planning & Scheduling for KMRL"** and **"Maximizing Section Throughput"** — but
**not** "Automatic Block Planning". The user was asked twice to verify the ID
and title against the live portal and confirmed **"ps number is correct"**, so
everything was built on SIH2026027. If a future session finds a mismatch, the
deck's PS ID/title (slide 1) and the prototype framing are the only places that
would need changing — the CP-SAT core applies to any of those three statements.

### The model
Decides whether and when to schedule each request, subject to: block must sit
wholly inside one traffic-free window on its own section; no two blocks hold a
section at once; per-department crew limits; per-request deadlines. Maximises
weighted value of work scheduled, then the slider's balance.

Two modes — **optimise** (requests optional, always returns a plan) and
**strict** (all mandatory; on failure returns the minimal conflicting set).

### The scenarios
| | Scenario | Purpose |
|---|---|---|
| A | Jaipur division · 3 sections · 8 requests · 5 days | baseline, ~40 ms |
| B | Jaipur–Gurgaon · 6 sections · 18 requests · 7 days | scaling, ~120–500 ms |
| C | 1 section, 1 night, 3 urgent jobs | **the conflict demo** |

**Scenario C is deliberately constructed** so SEC-A has a single 240-minute
window and R01/R02/R03 need 90 minutes each. *Any two fit* (180 of 240); all
three need 270 and cannot. So no pair is infeasible and the clash is genuinely
three-way — which is far more convincing than a two-way one. R04/R05 sit on
SEC-B and must never appear in the conflict set.

### The slider is a real trade-off (asserted in tests)
| Priority | Days used | Disruptive daytime windows |
|---|---|---|
| Protect service (0.0) | 7 | 0 |
| Clear urgent work (1.0) | 2 | 6 |

## 7 · BUGS FOUND AND FIXED — do not regress these

1. **CP-SAT's conflict set is not minimal.**
   `SufficientAssumptionsForInfeasibility()` returned *all five* requests on
   scenario C — technically sufficient, operationally useless. `model.py` now
   runs a **deletion filter** (`_minimal_conflict`) that drops each request and
   re-solves; what survives is irreducible. This is the single most important
   piece of logic in the project — the demo's best moment depends on it.

2. **Streamlit ignores `value` after a widget's first render.**
   Switching to scenario C left the "every request is mandatory" toggle at its
   previous state, silently killing the conflict demo. Fixed with a per-scenario
   key: `key=f"strict_{key}"`.

3. **First solve reported ~1050 ms** — nearly all CP-SAT warm-up. A
   `@st.cache_resource` warm-up solve now runs at startup so displayed times
   are steady-state.

4. **Solve time is not stable** (218 / 536 / 806 ms observed under load).
   The video script says **"well under a second"** and never a number. Do not
   reintroduce a specific figure.

5. **A test asserted a false property** — that all kept requests outrank all
   dropped ones. Untrue across *independent sections*: dropping a low-priority
   job on SEC-B frees no SEC-A capacity. Test rewritten to assert the real
   property (sheds only from the contested section).

6. **The slider shot recorded on scenario A**, because each Playwright context
   resets the app. `shot_slider` now selects B first — the script says "the same
   eighteen jobs".

### Environment gotchas
- **PowerShell 5.1 has no `&&`.** Give the user one command per line.
- **Windows console is cp1252** — `cli.py` detects this and falls back to ASCII
  rules rather than crashing on box-drawing characters.
- **`use_container_width` is deprecated** in current Streamlit → `width="stretch"`.
- The **Browser pane could not screenshot** in this environment ("not
  compositing frames"); Playwright was used instead.
